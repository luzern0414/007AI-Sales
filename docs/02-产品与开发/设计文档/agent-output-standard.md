## 二、事实、需求与分期控制

### 2.1 所有内容共用一个证据底稿

会议转写、甲方补充、历史会议和已授权项目资料先形成结构化底稿，四类文档均读取同一冻结版本。每项内容必须有稳定编号，能追溯到来源；修改底稿后生成新版本，不静默改写旧稿。

下表规定内容性质及写法。

| 内容性质 | 判定依据 | 输出方式 |
|---|---|---|
| 会议事实 | 可定位发言及原话 | 可写入纪要；未经校对的关键事实显示待核对。 |
| 明确决定 | 明确表达同意、确定、采用等，能说明决定主体 | 单列决定；发言人身份或权限未知时注明待确认，不能自动标为甲方批准。 |
| 明确需求 | 原话明确提出业务要求 | 进入需求清单，保留来源和确认状态。 |
| 乙方建议 | 技术实现、方案推导或人工补充建议 | 标为“乙方建议”或“初稿，待甲方确认”，不能变成会议结论。 |
| 未知与冲突 | 缺少字段或资料相互矛盾 | 写明具体待确认问题、影响及建议确认角色；不猜答案。 |
| 技术不可承诺 | 无可验证实现路径或前提无法满足 | 需求清单保留原始诉求与核查结论；不写成方案承诺，在系统能力说明中解释。 |

`source_kind`、`epistemic_status`、`confirmation_status` 分别记录来源、认知状态、确认状态，不能用一个“已确认”字段混淆三者。匿名说话人须人工映射；不能凭声线判断岗位、姓名或决策权。

### 2.2 单版是默认，分期需要当前项目证据

下表说明不同会议表述如何决定方案范围。

| 当前项目证据 | 方案处理 |
|---|---|
| 没有明确提出一期、二期 | `scope_mode=single_version`；标题、目录、正文、清单、模板和统计均按一个完整方案。 |
| 只说“先调研再开发”“先测试再上线” | 属于实施步骤，仍为单版；不得推导为一期、二期。 |
| 说“以后可能再考虑”但未确认分期 | 记入待确认问题或系统能力说明，不创建“二期展望”。 |
| 明确要求“本次做记账，下期做报销”，且范围与主体可追溯 | `scope_mode=explicit_phases`；只按会议明确的期次及归属组织，不能补造后续期次。 |
| 多次会议分期要求冲突 | 保留冲突，按经指定确认人的最新有效确认处理；未经解决不得发布确定性分期方案。 |
| 只有参考文件或文件名出现“一期” | 不构成当前项目分期依据；清除样板继承的期次文字。 |

`scope_mode` 由证据及人工确认产生，不能由模型凭经验自由设置。进入分期模式必须保存 `phase_evidence_ids`、明确范围、来源版本和确认记录；证据不足时回到单版讨论稿，并标记范围问题。

单版方案不得出现“一期范围”“二期展望”“暂不纳入（二期或待定）”“后续二期”等自拟分期表述。需求清单中需要记录被否决的分期原话时，仅允许在明确标注的来源摘录中保留，并与业务正文区分。模型不得把“V1.0/V1.1”文档修订号当成项目分期。

## 三、四类文档的结构

### 3.1 会议纪要

文件名以 `yyyymmdd_` 开头。未确认纪要标题或版本信息必须标明“讨论稿/待确认”；AI 自动生成不等于甲方认可。

下表列出纪要必须覆盖的信息。

| 章节 | 内容 |
|---|---|
| 会议基本信息 | 项目、主题、时间及时区、参会者、来源、录音是否完整、底稿版本。 |
| 现状与痛点 | 按业务主题记录现行做法、具体问题、相关来源。 |
| 需求与约束 | 需求编号、甲方诉求、规则、已有系统、数据、权限、部署及限制。 |
| 会议决定 | 决定内容、提出/确认人、来源；未定事项不得混入。 |
| 待确认问题 | 问题、影响、建议答复人；日期未知写“待确认”。 |
| 行动项 | 事项、负责人、交付物、截止时间、来源、状态；不能自动分配不存在的责任人。 |
| 来源索引 | 发言片段时间、来源文件页码/工作表及单元格、资料版本；离线阅读保留可读定位。 |

不逐字复述整场会议，不丢弃否定、金额、数量、期限、权限和排除条件；未听清的内容明确注明。

### 3.2 售前解决方案

方案遵循通用规范的章节顺序，按项目是否有硬件、AI、人工采集进行适用性裁剪。裁剪后一级章节连续编号，二级编号随之更新；不能为了模板完整添加无业务依据的功能或设备。

全文须有一条主线：第二章首节“总体方案”先给总体框架图和“各层说明”表，表中列出层次、职责、输入输出、对应章节。后续各章围绕框架中的层及其横向保障展开，不能独立堆砌模块；建设清单、建设原则的节号相应顺延。纯 Markdown 交付仍须给出完整的文字/表格框架；启用图形渲染后图表使用同一结构化框架，不另造结构。

同类设备统一按“用途／工作方式／采集数据／安装条件／与系统对接／怎么检验／限制”描述，每项 AI 功能统一按“能做什么／怎么实现／怎么检验／限制”描述。新增需求、模块、设备或数据源时，同步核对总体框架、建设清单、数据来源、业务线、实施计划、交付、验收、甲方配合、风险和系统能力说明，不能只增加一节。

下表规定章节、表格和配图。

| 顺序 | 章节 | 必要内容 |
|---|---|---|
| 封面 | 甲方/项目、方案标题 | 标题分两行，副题由 4–6 个关键词以“·”分隔，V1.0（讨论稿），`yyyy 年 m 月`。甲方名称未知则写“甲方名称待确认”。 |
| 目录 | 两级目录 | 仅一级和二级；Markdown 提供章节导航，Word 使用自动目录。 |
| 一 | 项目概况与建设目标 | 概述、概况图、基本情况表；问题／具体表现／解决思路；目标／建成后能做到什么；数据来源与用途图。 |
| 二 | 建设内容 | 先“总体方案”：框架图及各层说明／对应章节；再建设清单“类别／内容／数量”、建设原则“原则／说明”。设备数量未知写“按勘察确定”，未报价写“需另行报价”。 |
| 三 | 业务流程 | 业务线总图；业务线／怎么运转／主要参与人；关键输入、处理和确认步骤。 |
| 四（适用时） | 硬件方案 | 布置图、设备总览、安装供电网络与审批、输出数据、效果测试、选型限制、配套及运维。 |
| 五（适用时） | 数据采集方案 | 来源、字段、频率、责任人、提供方式、质量校验；人工报送有方式对比、推动措施和真实性说明。 |
| 六 | 平台功能 | 功能模块／主要内容；标准产品写清“按项目配置”，未核实已有功能不能标为“已有”。 |
| 七（适用时） | AI 功能 | 分工原则图；功能／使用人／实现方式／人工把关；每项说明能做什么、怎么实现、怎么检验、限制。 |
| 八 | 系统架构与部署 | 架构图、接口前提、部署对比与建议、服务器网络表、数据安全表。 |
| 九 | 实施计划 | 带里程碑的甘特图；时间／主要工作／产出／甲方配合；工期前提及不满足时影响。无依据的时间写“预计/初稿，待确认”。 |
| 十 | 交付与验收 | 硬件、软件、文档、服务分组交付；验收项／标准／验证方法，仅承诺能做到且能检验的内容。 |
| 十一 | 甲方配合事项 | 类别／资料内容／提供时间；事项／乙方建议／建议决定时间；与完整确认清单对应。 |
| 十二 | 风险与说明 | 风险／影响／应对；最后单列“系统能力说明”，写清条件和不承诺事项。 |
| 附录（适用时） | 指标口径等 | 有出处的指标定义、来源和必要规则；不复制内部调试日志。 |

图表数量由内容需要决定；每张图表之前有一句引导语。图号、表号各自全文连续；表题在上、图题在下。引用使用“见 3.5/见第六章”，避免依赖易变化的表号。

方案中每个功能必须回答“用什么技术实现、依赖什么数据/设备、什么情况下会失效”；不能回答时不作为交付承诺。AI 固定分工表述为：**AI 负责听懂问题和写文字，程序负责计算数字，人负责确认和决定。**

### 3.3 需求清单

需求清单不是功能建议合集。会议中的明确要求全部有去向：进入方案、等待确认、需要技术核查或由有权人员明确否决。不能因难实现而删掉甲方原始诉求，也不能把模板功能自动加入。

下表为业务需求表的固定字段。

| 字段 | 规则 |
|---|---|
| 编号、业务模块、需求名称 | `REQ-001` 等稳定编号；修订不重用已删除编号。 |
| 甲方要求、现状/痛点 | 忠实提炼原意，保留必须、禁止、例外等条件。 |
| 使用角色、业务规则 | 未知项标待确认，不推断审批权。 |
| 数据/接口/设备依赖 | 对应资料清单编号，说明提供者和技术前提。 |
| 实现方式、可行性结论 | 标“已核实/待核实/不可承诺”，注明核查依据。 |
| 验收方法 | 可实际检验，AI 文字不承诺准确率。 |
| 必需性/优先级 | 仅会议明确或人工确认后赋值，否则“待确认”。 |
| 来源、确认状态 | 发言时间或文件定位；待确认、已确认、已否决。 |
| 待确认问题、方案对应章节 | 未写入方案时说明原因，避免遗漏。 |

宽表在 Web 中支持横向滚动，Markdown 可分“需求总表”和按同一编号关联的“实施与验收表”；字段不因排版而丢失。方案需求覆盖统计由程序计算，不由模型估计。

### 3.4 甲方资料、权限与规则确认清单

采用样板“使用说明 + 清单 + 回收统计 + 专项填写模板”的形式；单版模式没有“一期清单/二期清单”，统一命名“确认清单”。不同业务模块可分节，不能强制分期。

下表规定主清单字段，继承样板的 12 列并明确权限信息。

| 字段组 | 内容 |
|---|---|
| 原样板固定 12 列 | 编号、分类、事项、需要准备的内容、用途、形式、交付格式、参考模板、必需性、建议责任方、状态、甲方填写／备注。 |
| 权限专项表 | 清单编号、系统、需开通权限、可替代的文件方式、不需要的权限、开通人、有效期、撤销方式、状态。主清单通过编号关联。 |
| 项目追溯字段 | 对应需求编号、提出依据、建议提供时间、甲方确认人、文件位置/版本、确认记录；在 Web 和 Markdown 关联表显示。 |

主清单状态采用样板值：待提供、进行中、已提供、已确认、不适用。“已提供”只说明交件，不证明业务规则批准。下表规定统计及业务判断。

| 判断 | 规则 |
|---|---|
| 回收率 | （已提供 + 已确认）÷（总项数 − 不适用）；分母为 0 显示“—”。沿用样板计算形式，但命名为回收率。 |
| 规则确认率 | 已确认的适用规则数 ÷ 适用规则数；“已提供”不计入。 |
| 开工条件 | 必须资料通过完整性检查，必须规则获指定人确认，必须权限获验证；不能只看回收率。 |
| 不适用 | 必须说明原因和确认人；不能由 Agent 为提高完成率自动设置。 |
| 默认状态 | 新生成项目全部待提供或待确认；模板示例不能显示为已交件。 |

专项填写模板按当前项目选择，下表说明如何从财务样板抽象，而非固化到财务行业。

| 样板形式 | 通用模板与关键字段 |
|---|---|
| 主体与账套 | 主体与现有系统：全称、类型、主体关系、系统/环境、主要业务、业务范围、备注。 |
| 业务范围 | 业务类型、发生部门、来源、业务量及周期、是否需要、当前责任角色、备注。 |
| 人员与角色 | 对接人、确认人、职责、回复时限；系统角色与数据范围；联系方式按必要最小化。 |
| 品类与核算口径 | 业务分类、判定规则、计算口径、字段来源、规则生效日期、例外、确认人。 |
| 报销与发票规则 | 业务规则表：标准、适用对象、异常处理、依据及确认人；仅财务项目使用原专用名称。 |
| 费用科目对照 | 编码/字段对照：源字段、目标字段、映射方式、缺失处理、责任人。 |
| 资料登记与拍照规范 | 清单编号、文件名、内容、数据期间、来源、提供人、备注；图片有清晰完整要求。 |
| 报销单据与审批 | 业务单据与审批：类型、适用场景、条件、审批角色、例外和职责分离。 |
| 工资与计薪规则 | 专项业务规则模板；仅实际涉及工资时采用，其他行业按需求生成对应专项表。 |

每条资料说明具体要什么、用途、样本期间/覆盖要求、原文件是否保留公式、脱敏范围、格式、责任角色和建议时间。数量/期间无来源时写“乙方建议，待甲方确认”；不机械要求财务样板的全部材料。

权限按最低必要范围填写，能用导出文件满足的业务不要求生产数据库或管理员权限。账号口令、密钥、网银凭证不进入纪要、方案、清单或模型提示词；授权在独立受控渠道交接。

## 四、写作、可行性与信息保护

下表将通用规范落实为生成规则。

| 规则 | Agent 必须执行的行为 |
|---|---|
| 面向业务负责人 | 用“怎么做、谁负责、做到什么程度”；首次必要缩写加中文说明，避免营销空话。 |
| 称呼统一 | 甲方首次用完整名称并注明简称；我方称乙方；没有全称则显式待确认。 |
| 数字有出处 | 保存数字、单位、口径、数据期间、来源；自拟阈值/权重标“初稿，待甲方确认”；不生成无依据准确率或节省比例。 |
| 计算可复核 | 金额、合计、数量、统计由程序计算并保存输入；AI 只解释计算结果。 |
| 责任可落地 | 说明角色、执行频率、产出和验收；未知负责人和日期保留待确认。 |
| 表格优先 | 超过 3 个并列要点或相同结构内容改成表；确需列表每条不超过两行。 |
| 软件可行性 | 标准产品依据已核实功能，以配置优先；接口可用性与授权是前提，不能默认存在。 |
| 硬件可行性 | 只写实际可输出的数据；精度以厂商书面承诺和联合测试为依据；写清安装审批、供电网络；先试装测试。 |
| AI 可行性 | 用可控的信息提取、文档问答、统计解释和起草；无数据预测、未经验证识别不能写成承诺。 |
| AI 验收 | 只承诺功能可用、数据与报表一致、人工确认流程跑通；不承诺生成文字准确率。 |
| 人工数据 | 明示只能提示异常，不能保证原始报送真实性；附推动与核验措施。 |
| 安全设备 | 辅助提醒不替代专业消防/报警设施；涉及安全联动须具备资质单位评估。 |
| 报价与敏感信息 | 面向甲方默认不含供应商成本和未授权报价；需要报价时单列并由用户明确提供/批准。 |
| 工期 | 写“预计”，说明前提与不满足时顺延；不能将样板工期复制为新承诺。 |

会后资料与口头描述不一致时，展示差异和相关数据依据，交指定人确认，不能让模型自动拍板。“规定期限未回复”不能视为同意，也不能从样板继承自动开工授权。

## 五、Markdown、Web、纪要 PDF 与正式方案 Word/PDF 的视觉规范

### 5.1 低饱和配色

下表是文档预览、图表和后续导出的统一色板。

| 用途 | 色值 |
|---|---|
| 主色／标题块／核心模块 | 藏青 `#1F3A5F` |
| 次色／层级标签／表格上下面框 | 石板灰 `#3E5C76` |
| 箭头及辅助元素 | 雾蓝 `#7489A3` |
| 表头／卡片底 | `#E6ECF2`、`#F5F7FA` |
| 首列／分组底 | `#F2F5F8` |
| 图形线条／表格内外细边 | `#D5DDE6`／`#A6B1BD` |
| 正文／次要文字 | `#1F2933`／`#66727F` |
| 少量风险、人工确认强调 | 暖金 `#A8875A`，底 `#F7F2EA` |

禁止高饱和彩虹分类、霓虹渐变和大面积暖金。强调同时有文字标签，不能只靠颜色。正文强调用字体和结构，不用彩色文字。

Markdown 文件保存内容和层级，字体、颜色、分页由查看器控制；平台预览负责落实色板。独立 `.md` 不依赖私有在线图片，不嵌入可执行 HTML。图表在首版以表格/文字表达；如有 Mermaid 预览必须提供同等可读文字说明，并明确普通 Markdown 查看器可能无法渲染。

### 5.2 后续 Word 排版参数

下表逐项保存通用格式规范的排版要求，后续实现不能由模型自由改写。

| 位置/项目 | 参数 |
|---|---|
| 纸张、边距 | A4 纵向；上 2.5 cm、下 2.3 cm、左/右 2.5 cm；正文宽不超过 16 cm。 |
| 页眉、页脚 | 距离 1.5/1.4 cm；宋体 9 pt；页眉右对齐“项目名 · 方案名”并加细线；页脚居中页码。 |
| 封面 | 项目名黑体 18 pt；标题黑体 26 pt、居中两行；副题宋体 14 pt 灰色及细分隔线；版本日期宋体 14 pt。 |
| 目录 | 标题黑体 16 pt“目　　录”居中；两级条目 12 pt，一级黑体、二级宋体；自动更新。 |
| 一级标题 | 黑体 16 pt；段前 18 pt、段后 10 pt；“一、二、三……”编号。 |
| 二级标题 | 黑体 14 pt；段前 12 pt、段后 6 pt；“1.1、1.2……”编号。 |
| 三级标题 | 黑体 12 pt；段前 8 pt、段后 4 pt；“1.1.1”或不编号。 |
| 正文 | 宋体 12 pt；1.5 倍行距；首行缩进 2 字符；段前后 0；强调用同字号黑体。 |
| 表格 | 表头黑体、内容宋体 10.5 pt；内容 1.25 倍行距；首列黑体居中；表头居中。 |
| 表格边框 | 上下 1.5 磅 `#3E5C76`；内框/左右 0.5 磅 `#A6B1BD`；表头 `#E6ECF2`。 |
| 表格布局 | 固定列宽及网格；名称列 2.4–3.2 cm，短值列 1.8–2.8 cm，其余给说明；表头跨页重复、行不跨页；单元格上下 0.1 cm、左右 0.2 cm。 |
| 分组行 | 通栏合并，黑体，底 `#F2F5F8`；仅名称首列使用该浅底。 |
| 图表题、注释 | 黑体 10.5 pt 居中；表题在上、图题在下；注释宋体 10.5 pt 灰色，“注：”开头。 |
| 图片 | 宽 15–15.5 cm 居中，图前引导语同页，图题紧跟；图内字号插入后不小于约 8 pt。 |
| 西文和数字 | 全部使用 Times New Roman；清除 Word 标题样式主题字体，避免混用。 |

约 25–30 页是完整方案的排版参考，不是字数硬指标；材料少时不编造内容凑页。过宽填报清单可单独作为确认材料，不能把 12 列硬压进方案正文导致不可读。

后续正式配图按照原规范：HTML/CSS 设计宽 1000 px，Chrome 渲染 PNG 为 3 倍清晰度；本地 Lucide 线性图标并登记 ISC 许可。图内步骤不超过 5 个字，说明不超过一行；逐图检查折行、截断、图例及配色。现阶段不制作这些图片或渲染代码。

## 六、质量检查与人工发布

不只设置一段提示词；开发时将下表规则落实为配置、结构校验、内容核查、人工确认和发布门禁。

| 检查项 | 检查方法 | 不通过处理 |
|---|---|---|
| 会议需求覆盖 | 每个已提取诉求必须映射到需求编号及去向；人工核对提取遗漏。 | 补齐或明确待确认，不能删除证据。 |
| 来源真实 | 检查 ID 存在、来源版本、摘录、时间/页码/单元格；语义支持再由模型辅助与人审。 | 撤销无依据事实或改为建议/未知。 |
| 分期一致 | 单版全文件检测期次标题、正文与统计；分期逐项查依据与归属。 | 停止正式发布，重新生成或修订。 |
| 方案结构 | 顺序、适用章节、图表引导语、编号、称呼与最终能力说明。 | 按模板修订。 |
| 总体主线与同步 | 框架各层有章节映射，同类内容有统一字段，变更同步到清单、流程、数据、计划、交付、验收、配合、风险及能力说明。 | 补齐遗漏映射与受影响章节，禁止只修一节后直接发布。 |
| 数字与承诺 | 数字来源、程序计算、报价授权、技术前提、AI 效果表述。 | 保留待确认或删除交付承诺。 |
| 四份文档一致 | 同一需求、依赖、范围、负责人、期限、资料编号逐项比对。 | 标记冲突，禁止将不同底稿拼成正式包。 |
| 权限与敏感信息 | 凭证过滤、最小权限、客户数据归属、导出内容检查。 | 去除敏感内容并要求必要人工复核。 |
| 排版 | Markdown 标题/表格可解析、Web 颜色和可读性；Word/PDF 另测字体、分页、目录、逐页渲染。 | 只交付实际通过检查的格式。 |
| 发布记录 | 确认人、确认时间、底稿及四份文档版本、质量报告。 | 保持讨论稿；AI 不能给自己盖章。 |

允许下载带明确“讨论稿/待确认”状态的 Markdown，以及同修订的会议纪要 PDF；身份、敏感信息和安全检查无论草稿还是正式稿都必须通过。纪要PDF任务须实际验证字体、分页、关键文本与逐页渲染，失败保留MD且不可标成功。正式售前方案PDF须来自已审核Word修订；正式文档包还须在全部内容硬规则通过且有人工确认后发布。模型事实核查不能证明绝无遗漏，必须保留人工回听、资料核对和逐项修订入口。
