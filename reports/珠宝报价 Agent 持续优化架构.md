# 让珠宝报价 Agent 从每次业务中积累可靠经验

结合 010ERP 的珠宝报价业务，我建议采用**确定性报价引擎、受控业务记忆、可调整的分析策略、离线评估发布**四者结合的架构。越用越好，应体现为更准确地找到可比报价、更少重复询问、更早发现遗漏条件、更能解释价格差异，以及更贴近实际的工时和损耗估计。它不等于模型在线自主修改金价、损耗政策或毛利底线。正式参数也可以持续调整，但需要业务负责人基于证据发布新版本；分析方法、案例检索和统计估计则有各自的优化通道。关键投入首先是记录“当时为什么这样报，后来发生了什么”，再让反馈转化为可审核、可验证、可撤回的经验。

本方案依据本地项目代码及公开官方资料综合设计，未使用企业真实成交、生产成本和回款样本，不能据此承诺收益比例或交付周期。现行一期架构规定敏感报价、工资不进入模型，因此近期可先完成本地结构化案例、反馈、规则检索和评估基础；涉及模型、嵌入与观测服务的部分，须按后续明确的数据使用边界实施。这里提出完整设计，不涉及修改 ERP 或上传业务数据。

## 一、把能学习的经验与必须受控的核算分开

### 正式规则需要可配置，而不是让模型随意改写

010ERP 当前报价已经具备 Decimal 计算、规则版本、计算依据、审核冻结和职责分离。这些应继续作为权威执行层。金价来源、取价时点、成色换算、计价单位、材料所有权、损耗政策、工费规则、税费、账期和毛利约束，都应是结构化、带有效期的业务资产，而非藏在一段提示词里。[现有报价计算](D:/Codes/010ERP/backend/app/finance/quotes/calculation.py)与[一期架构](D:/Codes/010ERP/docs/14-一期架构与客户修订对照.md)是这一层的基础。

例如，系统发现某工艺实际损耗持续偏离当前标准，可以生成“调整参数”的候选建议，展示样本范围、实际记录、异常批次、适用设备和预期影响。业务确认后发布新规则版本，注明生效日期。以后按新规则计算，过去报价仍保留原版本。这样既能改变规则，又能追溯谁批准了变化。

### 判断策略和统计估计有不同的学习方法

第一类可优化内容是**判断方法**：先核对哪些条件、怎样选可比历史、何时补问、哪些证据足以支持结论、怎样比较方案。第二类是**数值估计**：预计工时、实际损耗偏差、返工风险、交付延期和逾期可能性。这些可以在数据成熟后训练监督模型，输出估计范围并检查可靠性。模型估计应作为报价人员参考，不能悄悄替换正式核算参数。

第三类是**客户或场景经验**：某合同采用客户来料、某客户有特定验收要求、某工艺报价容易漏掉配件。它们需要范围和来源。“上次特批过低毛利”只是一笔例外案例，不能自动演化成该客户永久享有的政策。输出详略、常用筛选属于个人偏好，权限更低，也不能覆盖公司规则。

所以，遇到错误应先归因：字段错了，修事实；历史不可比，修检索；漏掉核查项，修分析方法；计算错了，修程序或正式规则；人工特批，保存例外；长期成本偏差，评估估计模型或参数变更。不能把所有问题都交给“优化提示词”。

## 二、先记录完整业务过程，再建立四类记忆

### 报价修订与商业机会是学习的数据骨架

当前 Quote 有 version、rule_snapshot 和 formula_trace 等信息，但更新报价会清空旧计算、对比结果，尚不等于完整的不可变业务历史；客户、集团、渠道、交易条款、订单及实际结果关联也需要补齐。当前按同主体、款式、材质的最近已审总价比较，容易混入重量、件数、成色和金价变化。[报价模型](D:/Codes/010ERP/backend/app/finance/quotes/models.py)与[报价服务](D:/Codes/010ERP/backend/app/finance/quotes/service.py)反映了这些现状。

建议保留 Quote 作为当前业务状态，增加 **QuoteRevision** 保存每次正式修订的不可变快照：输入、客户目标、材料所有权、数量重量、工艺、行情、条款、规则版本、计算结果和证据引用。再用 **Opportunity** 将同一商业机会的多轮报价归组。否则一位客户连续三次议价，可能被误当成三个独立成功或失败样本。

每次分析形成 **DecisionRecord**，绑定报价修订、参考案例、已知事实、解释假设、缺失信息、备选方案、建议依据和运行版本。保存可核查的分析依据与工具轨迹即可，不需要记录模型隐藏的内部思维链。

反馈与结果应分别建模。**FeedbackEvent** 记录谁修改了哪个字段、修改前后值、结构化原因、证据和复核情况；**OutcomeObservation** 记录客户回应、订单、交付、实际工时损耗、返工退货、成本结转及回款。批准、采纳、成交、实现利润、正常回款是不同信号，不能混成一个“成功”标签。

未回复不等于价格太高，未交付不等于零成本，尚未到期的款项不等于坏账。结果事件可以数周或数月后追加，需要 unknown、pending、成熟时间和观察窗口。金额、重量、单位、币种和时间必须结构化保存，不能全部塞进聊天摘要。

### 四类记忆各司其职，避免聊天内容变成公司政策

| 记忆类型 | 保存内容 | 如何进入下一次业务 |
|---|---|---|
| 任务记忆 | 当前报价修订、目标、已查证据、待补条件、工具结果、等待审批状态 | 恢复当前任务；恢复后检查是否过期 |
| 事实记忆 | 合同账期、结算方式、客户集团关系、工艺定义、有效行情快照 | 按权限、适用范围和有效期查询 |
| 案例记忆 | 当时条件、建议、人工修正、批准依据、成交及实际结果 | 找真正可比案例，展示成功与失败经验 |
| 方法记忆 | 经核实的检查步骤、比较方法、补证策略及例外边界 | 加入分析流程或检索提示，经过评估发布 |

个人展示偏好可以单独保存。LangGraph 将任务范围的状态与跨任务长期存储区分，LangMem 提供事实、情节和程序性记忆的组织机制，这与上述划分相契合；但框架不会自动提供本项目的财务审批和主体权限治理。([LangGraph Memory](https://docs.langchain.com/oss/python/langgraph/memory)，[LangMem Concepts](https://langchain-ai.github.io/langmem/concepts/conceptual_guide/))

每条长期记忆至少关联主体、客户或产品范围、来源及版本、业务有效时间、系统记录时间、状态、确认人、敏感等级、访问范围和替换关系。生命周期可采用“候选—核实—生效—被替代／过期／撤回”。自动抽取产生候选；已签合同或正式业务记录可按确定性同步规则形成核实事实；跨客户的方法经验需要更高等级审核。批准与生效分开，支持未来生效。

需要同时回答“当时业务规则是什么”和“系统当时知道什么”。今天补录的历史成本，不能假装过去报价时已经知道。发生冲突时先检查是否其实属于不同主体、合同、工艺和期间，再按业务确定的来源优先级处理；无法调和就保留冲突并补证，而不是让最新聊天覆盖旧事实。

记忆还必须能撤回。建立“来源—记忆—分析—建议”的依赖关系，原单据更正后停用相关记忆、清理缓存、标记未执行建议需重算。历史已执行决策保留当时证据，不静默改写。重复点赞和重复案例不能堆出可信度，模型自报的置信度也不能作为事实可信等级。

### 检索先判断适用性，再计算相似度

推荐顺序是：**主体与权限过滤 → 有效期与生效状态 → 结算、材质、成色、工艺等可比条件 → 关键词或语义候选 → 数值归一化与业务重排 → 上下文装配**。同样写着“黄金戒指”的报价，买料与客户来料可能完全不可比。文字相似度不能代替业务适用性，更不是正确概率。

上下文优先保留当前规则、当前事实、关键证据，再加入少量相关案例和已批准方法。不要把整段历史对话全部传给模型。跨主体比较必须事先获得相应读取权限，不能先检索全公司资料再让模型过滤；向量、缓存和观测日志同样受敏感信息边界约束。

一个假设场景可以体现改善：初次上线时，系统只看到某款加工费高于历史，建议核查。报价人员指出，新订单有不同镶嵌工序和更短交期，旧单不可比。系统先修正本次案例并记录原因，经过审核再形成“该类比较须核对工序与交期”的方法候选。后续遇到类似订单，先补齐这两个条件，再找可比案例。交付后用实际工时验证估计。这体现调查方法进步；一次成交不能证明提价策略有效。

## 三、线上报价与离线学习通过可靠事件连接

### 保留模块化单体，新增独立的辅助能力

建议继续使用 FastAPI、SQLAlchemy、Vue，不为 Agent 拆出一整套微服务。正式业务数据库仍是事实主库，记忆索引、案例摘要和预测结果是可以重建的辅助投影。项目目前开发默认 SQLite，生产拟采用 PostgreSQL，但生产部署、性能和恢复能力尚未验证，不能将其写成既成事实。

| 模块 | 职责及与现有系统的关系 |
|---|---|
| QuoteService／CalculationService | 正式修订、确定性计算、状态机、审批和业务写入 |
| EvidenceService／ContextBuilder | 组装授权事实、规则版本、行情、证据与任务上下文 |
| CaseRetriever／MemoryService | 可比案例、记忆生命周期、冲突、撤回和访问控制 |
| AgentRuntime／ToolGateway | 分析步骤、预算、检查点、补问、窄业务工具和输出校验 |
| FeedbackService／OutcomeProjector | 收集修改原因，关联订单、生产、财务的延迟结果 |
| Outbox／Worker | 可靠异步任务、重试、去重、失败隔离和人工重放 |
| Evaluation／ReleaseService | 数据集、回放、版本对比、灰度、观测和回滚 |

数据关系应明确为：Opportunity 包含多份 Quote；Quote 包含多份 QuoteRevision；每份修订可以有多个 AgentRun 与 DecisionRecord；反馈绑定具体修订、决策或步骤，结果关联商业机会及订单；MemoryItem 通过 MemoryEvidence 引用案例和原始来源，通过 MemoryUse 关联使用过它的决策；AgentRelease、EvalDataset、EvalResult 记录每次系统变化及验证结果。附件保留在文件或对象存储，数据库保存引用、版本和访问范围。

这种设计借鉴读写模型分离思想，但初期可以使用同一数据库，不需要独立读库，更不必全量改造成事件溯源。官方架构资料也指出，CQRS 需要处理读模型陈旧，而 Event Sourcing 增加并发、迁移和查询复杂度。([CQRS](https://learn.microsoft.com/en-us/azure/architecture/patterns/cqrs)，[Event Sourcing](https://learn.microsoft.com/en-us/azure/architecture/patterns/event-sourcing))

### 在线链路只完成本次报价与有依据的建议

用户发起分析后，系统先授权，固定报价修订和相关数据版本，调用正式计算服务。随后检索适用规则、案例与方法，程序完成料价、工费、重量和条款的标准化比较与情景计算。Agent 只在允许的数据边界内决定是否补问、解释差异、比较方案，并给出结构化结论：事实、假设、证据、缺失项、方案、适用条件和下一步。

工具接口应限定为“获取报价证据包”“检索可比报价”“计算候选方案”“保存分析草稿”等业务动作。初期不给任意 SQL 和任意写库权限。模型输出不能直接修改正式价格、规则或审批状态；用户选择方案后仍经过现有业务服务的权限、职责分离、并发版本和状态检查。

AgentRun 记录用户授权、报价修订、任务目标、步骤、工具结果引用、预算、超时和检查点。跨天补证或审批恢复时，重新检查权限、金价、政策和单据版本。旧建议的可复现性，不等于它今天仍可执行。任务完成与业务批准必须分开建模。

### 离线链路把反馈归因，再形成候选改进

业务保存报价修改或结果时，在**同一数据库事务**写入业务记录、反馈和 OutboxEvent。Worker 后续领取事件，构建案例、校验来源、分类错误、处理重复与冲突，产生候选记忆或候选方法，核实后发布。这样业务提交不会依赖模型速度，也避免报价成功但反馈丢失。事务 Outbox 的核心就是业务与事件原子落库，并由消费者处理重复。([Transactional Outbox](https://learn.microsoft.com/en-us/azure/architecture/databases/guide/transactional-out-box-cosmos))

采用至少一次投递和幂等消费，不承诺数据库与模型之间全局只执行一次。事件有唯一 ID，消费者以“消费者名称＋事件 ID”去重；任务有租约、心跳、重试次数、退避和失败隔离。同一报价按修订顺序处理，旧任务不能覆盖新投影。模型失败时，原有计算和人工审批仍能运行。

反馈界面应提供“事实错误、历史不可比、遗漏条件、公式口径、表达不清、建议不可执行、政策例外、客户条件变化”等原因，允许引用具体字段和证据。尽量自动捕获修改差异，减少额外录入。一次反馈先修正本次问题，不立即泛化；反复出现的经验也需要反例与适用条件，不能仅按频次晋升。

## 四、技术选型围绕治理与验证，避免先堆框架

### 记忆方案优先选择可控的关系存储

| 路线 | 对 010ERP 的适配判断 |
|---|---|
| 自建 MemoryService，必要时接 LangGraph／LangMem | 推荐起点。关系表承载来源、时态、权限和审核，框架承担复杂任务恢复或候选抽取；治理仍由应用负责 |
| Mem0 记忆服务 | 适合快速接入通用事实、偏好与检索，但必须加受控适配层，不能直接将抽取结果当正式条款；需核实所选版本的更新、删除与部署语义 |
| Graphiti 时态关系图 | 适合集团、合同、报价、订单、应收和争议的多跳历史调查；实体消歧与图运维成本较高，等关系调查成为瓶颈再引入 |

LangGraph 区分恢复用的 checkpointer 与跨任务 store，暂停恢复时节点可能重新执行，所以副作用必须幂等；首版明确状态机和数据库队列已经足够，复杂分支与长期恢复出现后再接入。([Persistence](https://docs.langchain.com/oss/python/langgraph/persistence)，[Interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts))

Mem0 当前 add 文档描述的默认抽取与追加机制，不应被理解为已自动完成本项目所需冲突消解和规则审批。Graphiti 提供时间事实、来源 episode 和混合检索，也不保证抽取关系正确。选它们是在购买通用机制，而不是把业务治理一并交出去。([Mem0 Add](https://docs.mem0.ai/core-concepts/memory-operations/add)，[Graphiti](https://github.com/getzep/graphiti))

检索先用关系条件和适配中文的全文搜索。有真实语义召回缺口、数据使用获许可且采用 PostgreSQL 时，再加 pgvector。先建立精确检索基线，数据规模和延迟确有需要时再评估近似索引。pgvector 文档提示近似扫描与过滤可能导致结果不足，因此不能把向量库的存在当作权限或召回问题已经解决。([pgvector Filtering](https://github.com/pgvector/pgvector#filtering))

### 提示和策略优化必须通过同一发布门槛

提示结构可分为稳定职责与约束、适用业务规则、当前任务上下文、输出结构四部分。改进重点是“哪些条件必须比较、何时拒绝归因、怎样补证”，而不是不断增加“深度思考”。每次变化明确针对哪类失败，先在固定评估集验证。

样本少时直接对比少量提示与检索方案即可。标注和评价标准成熟后，可以尝试 DSPy：MIPROv2 优化指令与示例组合，GEPA 可利用领域文字反馈产生文本改进候选。“选了不同结算方式的历史报价”比一颗差评更有价值。但优化器只产生候选，不能自行移动生产版本，也不能用成交率作为唯一文本奖励。([MIPROv2](https://dspy.ai/current/api/optimizers/MIPROv2/)，[GEPA](https://dspy.ai/current/api/optimizers/GEPA/overview/))

观测平台在 Langfuse 与 LangSmith 中选一种即可，用来关联运行轨迹、反馈、提示版本和评估样本。敏感原文默认不进入第三方日志；自托管也需要明确访问和保留策略。数值模型出现后再评估 MLflow 等模型登记工具，不必首日部署整套机器学习平台。([Langfuse Prompt Versions](https://langfuse.com/docs/prompt-management/features/prompt-version-control)，[LangSmith Evaluation](https://docs.langchain.com/langsmith/evaluation-concepts))

### 验证要恢复“当时已知的信息”

评估按时间向前切分，同一商业机会的报价修订必须在同一组，另设客户或款式留出以观察新业务泛化。检索示例、预处理和统计模型不能使用测试时期信息。特别要按系统当时可用时间过滤，今天补录的历史成本或条款更正不能进入过去的报价输入；延迟结果可以作为之后观察到的标签。([scikit-learn Cross-validation](https://scikit-learn.org/stable/modules/cross_validation.html)，[Feast Point-in-time Joins](https://docs.feast.dev/getting-started/concepts/point-in-time-joins))

回归案例应包含正常业务、缺可比历史、来料加工、一次性特批、过期金价、冲突反馈、异主体数据、审批中改价、重复事件和恢复失败。金额与权限用程序检查，业务解释由专家评审，模型裁判只作辅助。评价分为计算与权限正确性、证据和判断质量、审阅效率、长期业务结果；按主体、工艺、新旧品和金价波动分层，不能只看平均满意度。

商业目标应同时考虑实际经营贡献、成交、回款、交付能力和报价一致性。持续降工费可能提高成交率，却损害贡献和现金。历史成交预测也不是所有候选价格的需求曲线：销售挑选客户、客户质量、季节和金价都会造成选择偏差。因果效果需要明确假设与适当验证，不能直接由相关性推出；初期不自动随机对客试价。([DoWhy Causal Effects](https://www.pywhy.org/dowhy/v0.13/user_guide/causal_tasks/estimating_causal_effects/index.html))

发布顺序是离线回放、影子运行、限定主体和内部人员试用，再逐步扩大。影子版本不展示、不写业务、不发报价。试用按机会或团队固定版本，避免同一次谈判混入多个策略。硬性约束失败直接阻断，软指标依据业务风险与基线判断，不设脱离样本的统一准确率门槛。

AgentRelease 应绑定模型、提示、工具、工作流、检索、语义定义、估计模型、规则引用、记忆版本范围和评估版本。本次实际用了哪些记忆仍逐条记录。回滚不只是换提示：错误记忆要撤回、索引缓存要失效、受影响建议要追溯。恢复旧版本不能恢复已撤销权限或错误证据。

## 五、按数据成熟度推进，先证明能减少真实返工

**第一阶段，补齐记录和反馈。** 建立客户与商业机会关系、不可变报价修订、决策记录、修改原因和延迟结果；完善结算口径和标准化比较。当前敏感数据限制下，全部可先在本地由确定性服务、人工确认和结构化检索完成。完成门槛是能够复现一笔报价、说明多轮修改原因，并追踪后续订单和实际结果。

**第二阶段，启用受控案例记忆。** 先由人员选择高价值成功与失败案例，建设权限过滤、来源展示、过期、冲突与撤回。检验下一次是否少问已确认问题、少选不可比历史、少漏条款。还没有必要训练模型；整理案例本身就能改善体验。若引入模型，仅处理数据边界明确允许的内容，脱敏与合成数据可用于早期评估，不能假定脱敏后必然获准外发。

**第三阶段，优化分析方法和检索。** 在反馈归因与回归集稳定后，迭代补问顺序、可比排序、证据检查、方案解释，建立影子、有限发布和回滚。衡量人工返工、无依据判断、审阅时间和缺证据时的克制，而不只看文本流畅。进入下一阶段之前，应证明改善来自明确组件变化，并且没有引入新的越权或错误放行。

**第四阶段，使用成熟结果改善估计。** 先选择实际工时、损耗偏差等输入输出相对清楚的任务，确认样本覆盖、标签成熟度和预测误差；有概率输出则做校准。对于新工艺或样本稀少场景，扩大估计区间或回到人工。只有稳定任务、合规数据和足够标注具备，且提示与检索已显示明确上限时，再考虑微调；实时金价、合同和权限仍从工具查询。

同一基础可以扩展采购：把差异、补证、最终原因及处理结果形成案例，用于更快调查，而非自主放行；扩展记账：把已确认的业务分类沉淀为正式映射规则；扩展工资：记住经确认的解释与异议处理方法，计算和调整继续由规则、权限与审批控制。不同业务共享运行、反馈、记忆治理和评估机制，但不共享未经授权的数据和规则。

最终，平台应能回答三件具体的事：“为什么记住这条经验”“它适用于什么条件”“它曾影响哪些建议”。这比记忆数量更能决定系统是否可靠。真正可积累的优势，是企业逐步拥有可追溯的业务案例、经过验证的调查方法，以及能把实际结果带回决策的基础设施；更换模型或框架时，这些资产仍然保留。

公开资料证明的是上述存储、检索、恢复、优化和评估机制的可用性，不能直接证明本企业利润提升。技术方案研究以实际读取的官方文档和项目代码为主；部分通用搜索遇到访问挑战或无关结果，未将其当作证据。
