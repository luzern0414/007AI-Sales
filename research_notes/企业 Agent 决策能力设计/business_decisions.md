# 企业财务与经营 Agent：从报表到可追踪的决策支持

## 一、哪些真实技术机制能让企业 Agent 超越数据展示？

### Takeaway
最可复用的机制不是让模型说更多分析，而是把业务对象、计算口径、例外事件、可选行动、权限、人工复核、行动历史连接起来。应把厂商文档视为“功能设计证据”，不能视为已证明的经营收益；本次没有找到可复现实验支持这些厂商功能提升利润或降低坏账的幅度。

### Cited Findings
- Microsoft Account Reconciliation Agent 文档（2026-09-08 更新，production ready preview，明确 prerelease）：对账工作区先产生例外，再由 Agent 评价并建议动作；例外记录用户、自动化、Agent 的行动历史。设置包括业务模块优先次序、每日/月例外处理限额与预警；配置确认后才运行。当前处理例外列为 Voucher amount mismatch、Pending accounting transferred to general ledger；对前一种建议 Create journal entry，并允许选择 Reverse、Link transactions、Accept without change。Activity 有时间线，对 Reconciled 行动有撤销选项。该功能不是能够处理任何财务异常的通用财务专家，建议摘要还有 EN-US 限制。— [官方文档](https://learn.microsoft.com/en-us/dynamics365/finance/general-ledger/acct-rec-agent)
- Microsoft Collections coordinator summary：输入为客户逾期发票、支付历史、剩余授信；文档特别说明 **All calculations are done in Finance**，模型根据 Finance 数据及提示词生成说明。摘要范围是过去一年付款历史、未偿债务与过去六个月发票；提醒邮件生成草稿，由用户编辑、审核后发送。这是非常具体的“计算交给业务系统、语言模型交给解释与草拟”模式，也显示上下文窗口是业务定义而非随意把所有信息塞入模型。— [官方文档](https://learn.microsoft.com/en-us/dynamics365/finance/accounts-receivable/collectionscoordinatorsummary)
- Microsoft Cash flow forecasting（传统预测功能，不能包装成 LLM 新能力）：整合总账、应付、应收、预算、库存；覆盖未开票销售/采购订单、未付款发票、预算、需求/供应预测、外部导入数据、项目和税款等。销售/采购的现金时点拆成发货/交货至开票、账期、到期至实际付款，可按客户/供应商组覆盖默认值；明确警告项目预测再转入预算会重复计算。可以全量/增量计算、定期刷新、按公司隔离访问。— [官方文档](https://learn.microsoft.com/en-us/dynamics365/finance/cash-bank-management/cash-flow-forecasting)
- Microsoft Sales Qualification Agent 分 Research-only 与 Research and engage；前者调查线索、按目标客户画像评价适配并起草邮件，后者可自动接触、追问、判断意向、按交接规则交给销售；BANT（预算/决策权/需求/时间）作为显式评价框架。文档明确“doesn't replace your judgment or decision-making process”。平台可以把自主等级做成产品设置，而不是全局一个“自动执行”开关。— [官方文档](https://learn.microsoft.com/en-us/dynamics365/sales/sales-qualification-agent)
- Palantir Ontology Actions：Action 是根据预定义逻辑更改一个或多个业务对象属性的单笔事务，Action Type 规定属性/对象/链接变更和副作用，可校验有权角色、标准化参数、创建对象联系、触发通知。各应用共享同一动作逻辑与验证，最新对象数据可进入 writeback dataset。这里可复用的是“业务对象模型 + 有类型的行动契约 + 统一验证 + 写回”，不是聊天框自由生成任意 SQL 修改生产数据。— [官方文档](https://www.palantir.com/docs/foundry/action-types/overview/)

### Inferences
- 推荐把一次决策保存成对象：目标、指标定义、范围/时间、事实证据、计算脚本版本、假设、候选方案、风险约束、责任人、批准状态、执行记录、复查时间、实际结果。此为综合设计建议，非上述厂商共同实现的事实。
- “知识库”至少分三种：事实资料（合同/会议/制度等检索并保留版本权限）；业务语义（指标口径、对象关系、会计期间、币种、权责发生制等）；决策记忆（以前为何选择某方案、假设是否兑现）。只做文档向量库无法覆盖后两种。
- 运行时分层：LLM 做目标澄清、证据组织、候选假设、工具编排、建议表述；SQL/Python/ERP 做计算；预测模型做数值预测与区间；规则引擎做权限与阈值；审批/工作流系统处理真实行动。模型不是所有模块的替代品。
- 面向展示的“分析结论”升级为面向工作的“例外清单 + 影响大小 + 下一步需要验证什么 + 可以执行什么 + 何时回来复查”。

### Gaps
- Supplier Communications Agent 在微软综合页可见描述及链接，但详情路径当前 404，未用其作为具体能力证据。综合页称用户规则驱动采购任务自动化，但不宜据此编造动作/审批细节。— [综合页](https://learn.microsoft.com/en-us/dynamics365/copilot/ai-get-started)
- 没有足够时间可靠核验 Oracle/SAP 当期发布状态；未将其列为已部署解决方案。未发现可比、公开的经营收益因果评估。

## 二、财务经营场景应具备哪些判断能力，如何避免“看似会思考”？

### Takeaway
关键是从“发生了什么”升级到“哪些解释有证据、哪些还不确定、有哪些受约束的选择、需要什么追加信息”。方差归因、预测、情景模拟和因果推断是不同任务，不能统称根因分析。

### Cited Findings
- DoWhy 的因果效应工作流先建模假设，再识别效应是否能从现有数据估计，再估计，最后用反驳/稳健性检验挑战结论；四步为 model、identify、estimate、refute。该文档明确在选择估计算法前应先确定识别策略，支持后门、前门、工具变量等方法。不能让 LLM 从一张相关性报表直接断言某管理动作将改善经营指标。— [DoWhy 官方文档](https://www.pywhy.org/dowhy/v0.13/user_guide/causal_tasks/estimating_causal_effects/index.html)
- 现金流文档中的交易范围、到期至付款天数、客户/供应商分组参数和重复计算警告，说明业务数据建模和边界定义本身会改变预测结论；生成一份语言流畅的预测说明不能修复这些结构性问题。— [现金流官方文档](https://learn.microsoft.com/en-us/dynamics365/finance/cash-bank-management/cash-flow-forecasting)

### Inferences
- 以下是建议能力矩阵，不代表各厂商已经全部做到：
  - **现金预测**：核对银行/总账现金；按收付款时点建模；识别大客户延付、税款、工资、集中到期；做基准/悲观/乐观情景，展示区间和触发条件；比较催收、延后非关键支出、融资的现金与成本影响；每周回测。严禁把“利润好”当作“现金安全”。
  - **应收与催收**：除账龄之外连接争议、已承诺付款日、合同验收、历史支付、客户重要性、销售责任人；区分“愿意付但有争议”和“有违约风险”；排序依据应是预期回款增量与关系风险；先草拟提醒/内部工单，经授权才外发。
  - **利润与毛利下降**：先核对合并范围、币种、税前税后、收入确认、退货/折扣、一次性项目；再分价格、销量、组合结构、原材料、运费、产能/成本分摊；拆解需闭合到总差异并声明交互项/分解次序。之后提出解释假设并查反例（新旧客户、同品同渠道、促销与非促销、滞后、季节性）。数学分摊不等于干预因果。
  - **采购与库存**：连接订单、BOM、供应商交期、在途、需求预测、库存周转、缺货成本和现金约束；备选为加急/替代供应商/跨仓调拨/降低采购量，显式比较服务水平、持有成本、质量、违约与现金；把建议落实到有权限、版本和审批的业务动作。
  - **销售管道**：评估机会推进的证据、长期无互动、关键决策人缺失、交付能力、竞争与预算；不用模型自报信心代替历史校准成交概率；建议下一步澄清问题和责任人；重新估计胜率、时间与收入预测，保留为什么改分。
- 提示词中必须要求区分：**已观察事实 / 计算结果 / 业务解释假设 / 预测 / 建议**。不要要求“必须找到根因”“必须提出三条建议”；允许“数据不足暂不下结论”，并说明哪条新增数据最能改变决策。
- 针对利润案例的提示词骨架：“目标为在不降低最低服务水平与授信合规的前提下改善现金与毛利。先检查口径可比；按已定义公式计算并核对总差异；列主要解释及支持/反证；对可控因素做带明确假设的方案模拟；给出当前推荐、为何优于备选、哪些条件会改变推荐；输出需要审批的行动、负责人、复查日期与成功指标。关键计算调用工具；没有证据的影响幅度标记为假设，不写成事实。”
- “反证”要真正改变工具查询或方案选择。例如怀疑低价促销造成毛利下降，应检验同品类非促销订单、客户结构变化、折扣返利入账时点；不是让另一个模型只说一句“我检查过没有问题”。
- 好的主动性是基于业务目标与事件触发：发现现金安全阈值将突破、重大订单逾期、毛利偏离可解释范围时主动发起调查；通知按影响与可行动性筛选，并能因用户确认的合理例外而静默。

### Gaps
- 情景模拟依赖弹性、需求、交付等额外模型和业务假设；未有证据时，不能声称提价 2% 一定增加利润某个数额。可展示条件式算式和敏感性，不能称为已识别的因果效应。
- 本次未研究具体企业会计政策、行业特征、权限和历史数据质量；上述能力应由真实试点校准。

## 三、如何衡量决策质量及判断现有 Agent 能力边界？

### Takeaway
需要同时测“事实和计算是否正确”“决策是否合理、可执行且合规”“业务结果是否改善”；不能用回复更长、工具更多、用户点了赞或采纳率代替决策质量。金融领域基准能提示风险，但旧模型成绩不应外推为 2026 年产品能力上限。

### Cited Findings
- FinanceBench 2023：完整基准 10,231 个金融文档问答，公开样本 150 个含答案与证据；论文评估 16 种当时模型配置、共 2,400 份回答，报告 GPT-4-Turbo 加检索在该样本中 81% 为答错或拒答。必须保留年份、配置、样本与“答错或拒答”定义；这是历史金融 QA 结果，不能写成“今天金融 Agent 准确率只有 19%”。最值得复用的是黄金答案+证据文本+证据页码+推理类型+人工复核结构。— [作者原始仓库](https://github.com/patronus-ai/financebench)；[论文](https://arxiv.org/abs/2311.11944)
- FinGAIA 2025 原始仓库：407 道人工专家指导问题，涉及证券、基金、银行、保险、期货、信托、资管，分基础业务分析、资产决策支持、战略风控管理；涵盖网页浏览、文件、多模态、代码、计算等工具能力；作者报告其评测中 ChatGPT DeepResearch WA 48.9、人类专家 84.7。**发现质量问题**：当前中文 README 多处示例“问题”和“解题步骤”明显错配，例如核验平安银行年报的问题配成招商证券 K 线步骤，因此不能不加甄别照抄其数据与示例；不建议最终报告重点引用其排名，应把多工具任务分类作为借鉴，并注明为作者报告的单次基准。— [原始仓库](https://github.com/SUFE-AIFLM-Lab/FinGAIA)；[论文链接](https://arxiv.org/abs/2507.17186)
- 对账 Agent 的行动日志、限额、撤销、指定例外类型；Palantir Action 的参数、权限校验、事务和写回，是能直接复用的治理机制。其文档并未证明业务效益幅度。— [Microsoft](https://learn.microsoft.com/en-us/dynamics365/finance/general-ledger/acct-rec-agent)；[Palantir](https://www.palantir.com/docs/foundry/action-types/overview/)

### Inferences
- 建议优先测下面八类（均为产品评估设计建议，非现成统一行业标准）：
  1. **事实与计算正确率**：抽查金额、期间、币种、单位、分母、合并范围；查询结果可重放；利润桥分解总和闭合；证据确实支持结论。单独报告严重错误率，不能让大量简单正确回答稀释高风险错误。
  2. **假设与反证质量**：重要解释是否给出支持和反例；是否排除了数据延迟/口径变化；是否把相关性误写成因果；缺证时是否正确中止或补查。由财务/经营专家用盲评 rubric 评分。
  3. **预测质量与置信校准**：按时间向前回测，现金预测用 MAE/WAPE 等并按预测期和业务组分层；对于接近零和正负抵消的现金净额慎用百分比误差；报告预测区间覆盖率和宽度、回款/成交概率 Brier 分数、阈值事件漏报率。不直接采信模型口头“90% 有把握”。
  4. **决策效用与代价**：在与当时可知信息一致的历史案例中，比较 Agent、规则基线、业务专家的行动选择；模拟收益、最坏损失、资源占用、服务水平及机会成本；对关键假设扰动后推荐是否稳健。没有可靠反事实时标为模拟效用。
  5. **行动正确与合规**：动作是否在许可范围、对象是否选对、重复提交是否幂等、审批是否完成、参数/金额限制是否满足；零越权是门槛，不能用平均分容忍。
  6. **完成质量与人力成本**：端到端任务完成率、人工纠正/撤回率、实际审核时间、单位成功任务成本与时延；同时关注“用户很快同意但之后返工”的隐藏成本。
  7. **经营结果**：现金预测偏差、逾期回款、DSO、坏账、毛利、库存服务水平/周转、管道转化等按场景选少数主指标；设对照组/分批上线/匹配样本，控制季节性、客户组合和业务人员选择偏差。采纳率只能是使用指标，不能证明建议正确。
  8. **闭环学习与漂移**：逐次保存提出预测时的快照与假设，复查“预期→实际”偏差，区分输入差、模型差、执行差、外部变化；新知识和策略必须带来源、时间与适用条件，重大策略调整经验证再升级。
- 试点评测集建议选企业历史真实任务，以“当时能见到的信息”重放，包含缺数据、冲突口径、找不到根因、合理拒答、必须审批、需要升级给人、应当什么也不做等任务；否则只测到漂亮答题，测不到经营判断。
- 报告中可用一句主张：**Agent 的思考感，应来自能提出可检验的解释、说明权衡、在证据不足时补查、把承诺追到结果；而不是展示冗长内部思维链。**

### Gaps
- 本次没有复现 FinanceBench/FinGAIA，也未核验 FinGAIA 论文全文与版本，因此上述数字仅标为作者报告，不能当作独立复现结论。
- 尚无本企业的任务级黄金集、决策效用函数、错误损失、审批权限；无法给出可信的统一准确率/ROI 目标。应先做无写入影子运行与专家审核，再逐级授予行动权限。
- 本次真实搜索使用 Microsoft Learn Search API（query 包括 account reconciliation agent、collections coordinator agent、business performance analytics variance、supplier communications agent、sales qualification agent）及 GitHub 仓库搜索 FinGAIA；原始命中保存在 `.firecrawl/20261016-business-search-*.json` 与 `20261016-business-fingaia-github.txt`。Google/Bing 普通搜索遇到挑战页/不相关结果，未将其片段用作证据。原始资料正文保存于 `.firecrawl/20261016-business-*.txt`。
