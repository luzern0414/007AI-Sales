# 02 文档结构：章节骨架与两个版本

## 1. 总要求

- **一条主线**：开篇用一句话说清主线，并在“总体方案”给出总体框架图 + “各层说明”表，表中写明每层“详见第几章”；后面每章对应框架中的一层。
- **同类同模板**：同一类内容用同一张表的结构描述（见第 4 节）。
- **新增要同步**：新增一项设备或功能时，同步修改：框架图、建设清单、数据来源、指标、平台功能、权限、业务线、实施计划、交付、验收、资料清单、待决定事项、风险、能力说明。
- **完整方案**：不分期，不写“暂不纳入”“二期展望”。
- **篇幅**：完整版约 25–32 页，汇报版约 18–22 页。
- 每张图、每张表前有一句引导语；内容以表格为主，段落每段不超过 4 行。

## 3. 汇报版（给领导看）

**汇报版不是完整版的删减版，而是按领导视角单独成稿**（模板 `scripts/boss_template.py`，样板 `examples/深湾科创_build_boss.py`）。
完整版讲“怎么做、做到什么程度”；汇报版讲“为什么做、怎么想、建成什么样、能用在哪、新在哪、值不值”。
两版的设备、功能、能力边界必须一致，汇报版不得为了“好看”新增承诺。

| 项 | 完整版 | 汇报版 |
|---|---|---|
| 读者 | 甲方业务负责人、实施人员 | 甲方领导、决策层 |
| 文件名 | 《××实施方案》 | 《××建设方案（汇报版）》 |
| 版本标注 | V1.0（讨论稿） | V1.0（汇报版） |
| 篇幅 | 25–32 页 | 18–22 页 |
| 重心 | 硬件参数、功能说明、计划、验收、风险 | 思路、目标、架构、应用场景、AI、创新、价值 |
| 不写 | — | 实施计划、验收标准、甲方配合、风险细节、设备逐项说明 |

### 汇报版章节骨架

逻辑主线：**为什么做 → 做成什么样 → 怎么做 → 整体架构 → AI 核心能力 → 落地场景 → 创新与价值 → 建设内容**。
先目标后思路（先讲“要成什么样”，再讲“怎么做”）；先 AI 能力后场景（先讲“能做什么、做到什么程度”，再讲“用在哪”）。

| 章节 | 写法 | 图（fig_kit） | 表 |
|---|---|---|---|
| 总述（不编号） | **执行摘要，领导只看这一节也能看懂全貌。**不写大段文字，结构为：①“一句话概括”（两三行）；②“方案要点”两列表，分五项——怎么赋能（感知/汇聚/赋能）、AI 能做到（逐项带程度）、人来把关、对比传统（从“××”到“××”）、核心创新，每项内用①②③分点；③全景图；④一行“全文脉络” | `circle_flow`（感知—汇聚—洞察—预警—决策—服务，下方注明 AI 做到 / 人来把关 / AI 不做） | 要点｜内容 |
| 一、项目背景与挑战 | 概况两三句；挑战用 4–5 个短语概括（如“看不清、管不细、招不准、防不早、连不通”） | `kpi_overview` | 挑战｜具体表现｜带来的影响 |
| 二、建设目标 | 一句话总目标（愿景式，如“打造‘可感知、会分析、能预警、懂经营’的××，从‘××管理’升级为‘××管理’”）+ 4–5 个四字目标 | `principle_cards`（顶部总目标） | 目标｜建成后的样子｜主要支撑 |
| 三、建设思路 | “以××为基础、以××为牵引、以××为助手、以××为保障”；**三个转变**；**四个融合**（回答“怎么连成整体”）；**定制设计**（项目特点 → 对应设计） | `principle_cards`（顶部转变 + 下方融合） | 转变｜过去｜建成后；融合｜怎么融合｜带来什么；项目特点｜定制设计 |
| 四、总体架构 | “1+1+N”这类数字概括；架构图自上而下：服务对象 → 应用场景 → AI 层 → 平台 → 数据底座 → 感知层；各层说明写“详见第×章” | `layers` | 层级｜包含内容｜作用；架构特点 |
| 五、AI 赋能 | 开头一句承上启下；5.1 定位与原则（程序算数、AI 起草、人来确认）；5.2 **AI 能做到什么程度**（如实写程度和边界）；5.3 **与传统方式对比**（按管理环节逐项） | `principle_cards` | AI 能力｜能做到的程度｜人的角色；管理环节｜传统方式｜AI 赋能后 |
| 六、核心应用场景 | 全景图分 2–4 组共 6–10 个场景；每个场景一节，标题“场景×：名称——一句价值”，先写一段“谁在什么情况下怎么用”，再用统一五行表 | `scenario_grid`；关键场景配 `hub`（多源融合画像）、`chat_mock` | 谁在用｜以前怎么做｜系统能做什么｜AI 能做什么｜带来的变化 |
| 七、创新点 | 一句话概括（“一个……、一套……、一种……”）；6–8 个创新点，每个与传统做法对比 | `innovation_grid` | 创新点｜为什么有价值 |
| 八、建设价值 | 按对象写：管理层、各业务团队、客户/商户、集团 | — | 对象｜价值 |
| 九、建设内容 | 硬件布置图 + 硬件表（数量、报价状态）；软件与服务；部署与安全（含第三方接口等前提） | `zone_cards` | 设备｜位置｜采集数据｜数量｜说明 等 |

### 汇报版写作要点

- **场景先于技术**：先写“谁用、怎么用、有什么变化”，技术名词尽量不出现。
- **系统与 AI 分开写**：每个场景都分别说明“系统能做什么”“AI 能做什么”，让领导看清 AI 的具体作用；没有 AI 参与的写“数据自动汇总”等，不硬凑。
- **创新要有对比**：每个创新点都写“传统怎么做 → 本方案怎么做 → 为什么有价值”，避免空喊“创新”。
- **定制要有对应**：每条定制设计都对应项目信息卡中的一个真实特点。
- **价值不编数字**：没有依据的效益数字（如“效率提升 50%”）不写，用定性描述。
- **大段文字改表格**：超过 4 行的综述性文字，改为“一句话 + 分项表格（单元格内①②③分点）”。
- **示意图标注**：AI 对话等界面示意图必须注明“示意图，数据为示例”。
- **边界一句带过**：在相关场景中用括号注明关键边界（如“辅助提醒，不替代消防设施”），前提条件放在“部署与安全”。

### 简易汇报版（仅删减）

如用户只要求“删掉某些章节”，仍可用完整版脚本的 `d.mute = BOSS` 机制生成；删除的章节应排在各章或全文末尾，使保留章节编号连续，并告诉用户与原章节号的对应关系。

## 4. 统一模板表

**设备模板表**（每类硬件一张，两列：项目｜说明，列宽 2.6 + 13.4cm）：

| 项目 | 写什么 |
|---|---|
| 用途 | 解决什么问题 |
| 工作方式 | 原理，一两句，通俗 |
| 采集数据 | 只写设备实际能输出的数据 |
| 安装条件 | 供电、网络、位置、施工时间、审批、需谁配合 |
| 与系统对接 | 平台是否原生支持；不支持时写清接入路径 |
| 怎么检验 | 可操作的方法；精度以厂商书面承诺为准 |
| 限制 | 做不到、会失效、不能替代什么 |

**功能模板表**（每项 AI/软件定制功能一张）：能做什么｜怎么实现｜怎么检验｜限制。

**对比表**（方式 A/B/C）：对比项（做法、数据安全/准确性、额外投入、上线速度、建议）× 各方式；最后一行给出“建议”。
