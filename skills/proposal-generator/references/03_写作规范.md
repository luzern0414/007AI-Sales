# 03 写作规范：口径、通俗化、不过度承诺

## 1. 读者与语气

- 读者是甲方业务负责人和领导，不是技术人员。写“建成后能做到什么、谁来做、做到什么程度”。
- 语气平实、肯定，不用“赋能、抓手、闭环生态、全域、颠覆、打造标杆”等空话堆砌。
- 每段不超过 4 行；结构相同的要点（名称 + 说明）超过 3 条，一律做成表格。
- 列表能用表格就不用项目符号；确需列表时每条不超过两行。
- 每张图、表之前有一句引导语（“……如下：”“……如下图所示：”）。
- 强调用 `**黑体**`，每段最多一处，不用彩色字。

## 2. 称呼与用词

| 场景 | 写法 |
|---|---|
| 甲方首次出现 | 写全称，后注“（以下简称“甲方”）” |
| 我方 | “乙方” |
| 第三方产品 | 写品类（“商业运营平台”“电表厂商的采集平台”），不写未授权的供应商名称 |
| 时间 | “预计 14 周”“第 3–6 周”“启动前”，范围用短横“–” |
| 数字 | 阿拉伯数字，千分位“3,010.65㎡”；百分数“10.7%”；数与单位间按中文习惯（“92 台”） |
| 章节引用 | “见 3.2”“详见第四章”；不引用“表 9”这类会随增删变化的编号 |

## 3. 术语通俗化（首次出现时）

| 不要写 | 改写为 |
|---|---|
| OCR | 文字识别（OCR） |
| RAG、向量化、Embedding | 知识库检索（不写技术名） |
| UAT | 甲方试用验收 |
| SOP | 岗位操作手册 |
| 熔断、限流、重试 | 出故障时自动重试或切换备用模型 |
| 指标口径层、语义层 | 统一指标库 |
| VLAN | 单独划分的网段 |
| Docker、容器化 | 容器化打包，升级和复制更方便 |
| 精益价值流分析 | 精益诊断（把业务从头到尾拆开，找出等待、重复、返工） |

## 4. 数字与事实

- 所有数字来自甲方资料或可核实的公开来源；在信息卡中有出处。
- 自己拟定的权重、阈值、指标口径写“初稿，以《规则确认单》确认为准”。
- 查不到可靠依据的行业数值不写具体数，写“按甲方确认”。
- 资料间冲突的数字不擅自取舍，列入待确认事项。

## 5. 技术可行性核查（写每个功能前过一遍）

每个功能回答三个问题：**用什么实现？依赖什么数据/设备/接口？什么情况下会失效？** 答不清的不写。

| 类别 | 规则 |
|---|---|
| 设备 | 只写设备实际能输出的数据（如客流计数器只承诺人次，不写停留时长、热力、动线、年龄性别，除非选型明确支持）；精度以厂商书面承诺为准，双方现场联合测试；写清供电、网络、位置、施工时间、审批；新设备先试装再批量；未报价标“需另行报价”，数量不定标“按勘察确定” |
| 安全类设备 | 写“辅助提醒，不替代消防设施和燃气报警装置”；燃气切断等联动写“须由具备资质的单位评估实施”，不默认承诺 |
| 计量类设备 | 用于结算的电表须经法定计量检定；远程通断电涉及商户权益，默认不启用 |
| 采集类设备 | 写清采集范围（如小票打印机只能采到打印小票的交易，外卖订单采不到），给出覆盖不到时的替代方式 |
| 第三方平台 | 以产品已有功能为准；需要其开放接口的，写成开工前提和第一条风险；平台自带的能力（如问答、知识库）写“配置”，不写“开发” |
| AI | 只做成熟可控的事：规则计算、文字识别 + 信息提取、按统计结果起草文字、基于文档的问答。效果不稳定的不写：照片自动识别违规、没有数据来源的智能推荐、缺少历史数据的预测 |
| 人工报送数据 | 写“系统只能提示明显异常，不保证完全真实”，并给出管理推动措施（合同条款、与评分挂钩、回馈对方、交叉检查） |
| 工期 | 写“预计”，列出前提条件表；硬件需逐户施工、逐家配置的，工期要留够 |

## 6. 不承诺清单（写进“系统能力说明”）

- 未覆盖范围的数据（如未装设备的通道）
- 人工报送数据的真实性
- AI 生成文字的准确率；预警命中率；照片识别
- 安全类设备替代消防设施
- 与未授权系统的接口直连或写入
- 设备精度超出厂商书面承诺的部分

## 7. AI 固定表述

- 原则：“程序负责计算数字，AI 负责理解问题和起草文字，最终由业务人员确认。”
- 五道防线：只用既定指标、数字程序回填、回答注明出处、无依据不回答、人工确认生效。
- 验收：“功能可用、数据与系统报表一致、人工确认流程跑通”；“AI 生成的文字属于辅助内容，不单独作为准确率指标验收。”

## 8. 敏感信息

- 不写账号、密码、密钥。
- 供应商成本价、报价默认不写进面向甲方的方案；需要时单列章节并经用户同意。
- 个人信息（手机号、身份证）不进方案。
